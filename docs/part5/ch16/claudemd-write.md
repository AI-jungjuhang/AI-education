# 좋은 CLAUDE.md 쓰는 법

!!! abstract "이 페이지에서 배우는 것"
    - 메모는 ==짧고, 구체적이고, 서로 부딪히지 않을 때== 잘 지켜져요.
    - 공식 문서의 기준은 한 파일에 약 200줄 이내예요.
    - 우리 채널 프로젝트의 실제 CLAUDE.md로 좋은 점과 아쉬운 점을 봐요.

## 1. 모호한 말은 안 지켜져요

"정리해서 써 줘"는 사람도 알아듣기 어려워요. 공식 문서가 드는 예를 우리말로 바꾸면 이래요.

| 흐릿한 지시 | 확인할 수 있는 지시 |
|---|---|
| 코드를 깔끔하게 | 들여쓰기는 칸 두 개로 |
| 바꾼 뒤 검사해 줘 | 커밋 전에 `npm test`를 실행해 |
| 파일을 잘 정리해 | API 처리 파일은 `src/api/handlers/`에 둬 |

"했는지 안 했는지 확인할 수 있는 말"로 쓰는 게 요령이에요.

## 2. 짧게, 묶어서, 부딪히지 않게

- **짧게**: 한 파일에 약 200줄 이내가 권장이에요. 길수록 기억 공간을 더 쓰고 잘 안 지켜져요.
- **묶어서**: 제목과 글머리 기호로 나눠요. 빽빽한 문단보다 잘 읽혀요.
- **부딪히지 않게**: 두 지시가 서로 반대면 Claude가 아무거나 고를 수 있어요. 가끔 오래된 지시를 지워 줘야 해요. `/doctor prompt-audit`를 실행하면 Claude가 낡았거나 서로 모순된 지시를 찾아서 고칠 점을 제안해 줘요(v2.1.283 이상에서 쓸 수 있고, 내가 요청하기 전에는 파일을 바꾸지 않아요).

메모에 넣을 것과 넣지 않을 것도 나눠야 해요. 항상 필요한 사실(명령어, 규칙, 폴더 설명)은 메모에, 여러 단계로 된 작업 절차는 5.5의 스킬에 넣어요.

## 3. 실제 예: 이 책 프로젝트의 CLAUDE.md

이 책 저장소의 CLAUDE.md는 대략 이런 모양이에요. 항목만 소개해요.

- 책 이름과 부제, 사이트 주소에 개인 이름을 넣지 않는다는 규칙
- 책 구조(부 > 장 > 절 > 주제)와 독자
- 문체 규칙: 내용은 높게, 설명은 10살 눈높이
- 작업 순서: 원전 링크 확인 → 작성 → 빌드 → 디자인 점검 → 커밋
- 개발 브랜치 이름과 빌드 명령

잘된 점은 **빠뜨리기 쉬운 결정**(이름 규칙)을 적어 둔 거예요. 코드나 파일을 보고는 알 수 없는 것들이죠. 아쉬운 점은 영상 확인 방법 같은 긴 절차가 섞여 있다는 거예요. 이런 건 스킬로 옮기면 메모가 가벼워져요.

!!! tip "10살 눈높이 한 줄 요약"
    메모는 짧게 쓰고, "했는지 확인할 수 있는 말"로 써요.

!!! note "★ 한 걸음 더 (심화)"
    메모가 커지면 `.claude/rules/` 폴더에 주제별 규칙 파일로 나누고, 특정 파일 종류에만 적용되게 범위를 정할 수 있어요. `@경로`로 다른 파일을 불러올 수도 있지만, 불러온 내용도 기억 공간을 쓰는 건 마찬가지라 길이를 줄여 주지는 않아요. `/compact` 뒤에는 메모가 다시 읽혀요. 그래서 대화 중에 한 말과 달리 메모에 적은 규칙은 요약 후에도 살아남아요.

## 직접 해보기

내 프로젝트(또는 이 책 폴더)의 CLAUDE.md를 열어서 지시 세 개를 골라요. 각각 "했는지 확인할 수 있는 말"인지 보고, 흐릿한 건 고쳐 써 봐요.

## 오늘 바로 써먹기

```text
CLAUDE.md를 읽고 서로 부딪히거나 낡은 지시가 있는지 찾아 줘. 고치지는 말고 목록으로만 알려 줘.
```

- 정말 중요한 규칙은 맨 위에 올리고, 이유를 한 줄 덧붙이기
- 새 규칙은 "무엇을, 어디서, 어떻게" 한 줄로 쓰기

## 자주 하는 오해

- "길게 쓸수록 잘 알아듣는다?" 반대예요. 길면 기억 공간을 더 쓰고 지켜질 확률이 떨어져요.
- "메모를 한 번 쓰면 끝이다?" 프로젝트가 바뀌면 메모도 낡아요. 가끔 점검해요.
