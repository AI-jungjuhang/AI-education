# 계획하고, 행동하고, 확인한다

<p class="ep-meta"><span>14장 · 14.1</span><span>읽는 시간 약 6분</span><span>2026-11-07</span></p>

!!! abstract "이 페이지에서 배우는 것"
    - 에이전트의 핵심 모양은 =="계획 → 행동(도구 사용) → 결과 확인 → 다음 결정"을 반복하는 고리==다.
    - 이 고리를 짜는 몇 가지 대표 방식(체인, 분류, 병렬, 지휘자, 평가자)이 있다.
    - 고리에는 사람이 확인하는 지점과 멈추는 조건을 넣어야 한다.

## 1. 보물찾기

보물찾기를 한다고 생각해 보세요. 쪽지를 읽고(계획), 그 장소로 가고(행동), 쪽지를 찾았는지 확인하고(결과), 다음 쪽지에 적힌 곳으로 가요(다음 결정). 보물을 찾을 때까지 이 고리가 돌아가요.

에이전트가 일하는 모양이 이래요. 이전 페이지에서 본 정의처럼 **환경의 반응을 보며 반복**하는 거예요.

!!! tip "10살 눈높이 한 줄 요약"
    에이전트는 **쪽지를 읽고, 가 보고, 확인하고, 다음 쪽지로** 가는 보물찾기 고리를 돌아요.

## 2. 한 바퀴의 모양

1. **목표를 받아요.** 사람이 일을 알려 줘요.
2. **계획해요.** 무엇을 해야 할지 정해요.
3. **행동해요.** 검색, 파일 읽기, 코드 실행 같은 도구를 써요(13장).
4. **결과를 봐요.** 도구가 돌려준 내용을 읽고 진행 상황을 판단해요.
5. **계속할지 정해요.** 더 해야 하면 2번으로, 끝났으면 멈춰요.

Anthropic의 글은 이 과정에서 **중간 점검 지점이나 막혔을 때 사람에게 묻는 것**, 그리고 **최대 반복 횟수 같은 종료 조건**이 통제를 유지하는 데 흔히 쓰인다고 설명해요.

## 3. 고리를 짜는 다섯 가지 방식

같은 글은 에이전트의 바탕이 되는 **워크플로 패턴** 다섯 가지를 소개해요.

| 방식 | 하는 일 | 일상의 비유 |
|---|---|---|
| 프롬프트 체인 | 일을 **정해진 순서의 단계**로 나눠서, 앞 단계의 결과를 다음 단계가 받아요. 중간에 점검(관문)을 넣을 수도 있어요 | 이어달리기 |
| 라우팅 | 입력을 **분류해서** 알맞은 전문 처리로 보내요 | 병원 접수 창구 |
| 병렬화 | 나눌 수 있는 일을 **동시에** 돌려요(나눠 맡기기). 또는 같은 일을 여러 번 시켜 **다양한 결과를 모아요**(투표) | 모둠 과제 분담, 여러 번 풀어 비교하기 |
| 지휘자-일꾼 | 중앙의 모델이 **일을 그때그때 쪼개서** 일꾼 모델들에게 맡기고 결과를 합쳐요 | 감독이 현장 보고 일꾼 배치 |
| 평가자-개선자 | 한 모델이 답을 쓰고 다른 모델이 **평가와 피드백**을 해서 고쳐 가요 | 글쓰기와 퇴고 |

글에 따르면 **지휘자-일꾼**은 병렬화와 모양은 비슷하지만 **하위 일을 미리 정하지 않고 입력에 따라 정한다**는 점이 달라요. 예를 들어 코딩에서 몇 개의 파일을 어떻게 고쳐야 하는지는 일마다 달라서 미리 알 수 없어요. **평가자-개선자**는 평가 기준이 분명하고 반복해서 고치면 실제로 나아지는 경우에 알맞아요.

## 4. 고리에서 중요한 것

- **종료 조건:** 끝나는 때와 최대 횟수를 정해요. 정하지 않으면 계속 돌 수 있어요.
- **환경의 반응:** 행동의 결과를 정말로 읽어야 해요. 실패했는데 성공한 것처럼 진행하면 안 돼요.
- **사람의 점검:** 중요한 지점마다 멈추고 사람의 승인을 받아요.
- **기록:** 무엇을 했는지 남겨야 나중에 되짚어 볼 수 있어요.

!!! note "★ 한 걸음 더 (심화)"
    - 병렬화의 "투표"는 3장의 **같은 질문을 여러 번 해서 비교하기**와 같은 생각이에요. 같은 일을 여러 번 시켜서 서로 다른 결과 가운데 더 믿을 만한 것을 고르는 방식이에요.
    - Anthropic은 별도의 글 *Effective context engineering for AI agents*(2025-09-29)에서 에이전트가 긴 일을 하면서 컨텍스트를 어떻게 관리할지 다뤄요. 이 책에서는 제목과 날짜만 확인했어요. 에이전트가 오래 일할수록 컨텍스트 창(11장)이 채워져서 이 문제가 커져요.
    - 글은 "복잡도를 더하는 건 결과가 눈에 띄게 좋아질 때만"이라고 반복해서 말해요. 성능을 재고 개선하는 것이 핵심이에요(15장).

## 직접 해보기

일상의 일 하나를 고리로 쪼개 보세요. 예를 들어 "주말 가족 나들이 계획 세우기".

```text
목표: 이번 주말에 비가 와도 갈 수 있는 가족 나들이를 계획해 줘.
다음 순서로 진행하고 각 단계가 끝나면 나에게 보여 줘.
1) 후보 3곳을 제안해 줘.
2) 내가 하나를 고르면 이동 시간과 비용을 알아봐 줘.
3) 내가 괜찮다고 하면 일정표를 만들어 줘.
```

- 각 단계에서 내가 멈춰서 확인하는 지점은 어디인가요?
- 에이전트가 검색 도구를 가졌다면 어느 단계에서 도구를 쓸까요?

## 오늘 바로 써먹기

1. **"계획을 먼저 보여 줘"를 습관으로 하세요.** 고리가 돌기 전에 방향을 점검할 수 있어요.
2. **단계마다 멈추는 지점을 정하세요.** "각 단계가 끝나면 나에게 확인받고 다음으로 가"처럼요.
3. **종료 조건을 말해 주세요.** "5번 시도해도 안 되면 멈추고 알려 줘".
4. **결과를 직접 확인하세요.** 에이전트가 "성공했다"고 말해도 실제 결과를 보세요.
5. **평가 기준을 정해 주세요.** "이 기준에 맞는지 스스로 검토하고 고쳐 줘"는 평가자-개선자의 아주 작은 버전이에요.

## 자주 하는 오해

- "에이전트는 한 번에 모든 계획을 세우고 실행한다" → 결과를 보며 계획을 고치는 반복이에요.
- "고리를 많이 돌릴수록 좋은 결과가 나온다" → 횟수가 늘면 비용도 늘고 오류가 쌓일 수 있어요.
- "여러 모델이 협력하면 항상 더 낫다" → 글은 단순한 방법으로 안 될 때만 복잡하게 하라고 권해요.
