# 도구를 잘 설계하기

<p class="ep-meta"><span>15장 · 15.1</span><span>읽는 시간 약 6분</span><span>2026-11-07</span></p>

!!! abstract "이 페이지에서 배우는 것"
    - 에이전트의 일은 도구의 질에 크게 좌우되고, 도구는 ==사람을 위한 도구와 달리 "AI가 읽고 쓰는" 도구==여야 한다.
    - Anthropic은 도구를 만들 때 다섯 가지 원칙을 말한다: 적절히 고르기, 이름으로 구분하기, 의미 있는 결과 돌려주기, 토큰 아끼기, 설명을 정성껏 쓰기.
    - 개발자가 아니어도 "AI에게 줄 자료와 도구를 정리하는 일"에 같은 생각을 쓸 수 있다.

## 1. 새 직원에게 주는 도구함

새 직원에게 공구함을 주는데, 서랍마다 이름표가 없고 도구가 수백 개라면 어떨까요? 뭘 써야 할지 몰라 헤매겠죠. 반대로 서랍마다 "이럴 때 이걸 쓰세요"라고 적혀 있고 필요한 도구만 담겨 있으면 일이 빨라져요.

에이전트에게 주는 도구도 마찬가지예요. Anthropic의 도구 설계 글(*Writing effective tools for AI agents*, 2025-09-11)은 이렇게 시작해요. MCP(13장)를 쓰면 에이전트가 수백 개의 도구를 가질 수도 있는데, 그 도구들이 **효과적**이려면 어떻게 만들어야 할까요?

!!! tip "10살 눈높이 한 줄 요약"
    도구함은 **서랍마다 이름표와 사용법**이 있어야 하고, **꼭 필요한 도구만** 있어야 해요.

## 2. 도구는 "예측 가능한 시스템과 예측하기 어려운 시스템 사이의 약속"

글은 이렇게 설명해요. 컴퓨터 프로그램은 같은 입력에 항상 같은 출력을 내는 **결정적** 시스템이에요. 그런데 에이전트는 같은 조건에서도 다르게 반응할 수 있는 **비결정적** 시스템이에요. 보통의 소프트웨어는 결정적인 시스템끼리의 약속이지만, 도구는 **결정적 시스템과 비결정적 에이전트 사이의 약속**이에요. 그래서 에이전트가 도구를 **어떻게 읽고 오해할 수 있는지**를 생각해서 만들어야 해요.

## 3. 다섯 가지 원칙

글은 도구를 만드는 핵심 원칙으로 다섯 가지를 꼽아요.

| 원칙 | 뜻 | 일상 비유 |
|---|---|---|
| 알맞은 도구를 고른다 | 만들어야 할 도구와 만들지 않아야 할 도구를 가려요 | 공구함에 필요한 것만 |
| 이름으로 경계를 나눈다 | 비슷해 보이는 도구들이 **기능의 경계가 분명하게** 이름으로 구분되게 해요 | 서랍마다 이름표 |
| 의미 있는 맥락을 돌려준다 | 도구의 결과가 에이전트가 **다음 판단에 쓸 수 있는 정보**를 담게 해요 | 쪽지에 "다음엔 여기로"까지 적기 |
| 토큰을 아낀다 | 도구의 응답을 **토큰 효율**을 생각해서 줄여요(컨텍스트 창은 한정돼요, 11장) | 보고는 짧고 핵심만 |
| 설명을 정성껏 쓴다 | 도구 설명과 규격을 **프롬프트 엔지니어링**해요 | 사용 설명서 |

## 4. 설명서를 쓰는 법

글은 도구 설명을 쓰는 방법을 이렇게 말해요. 설명은 에이전트의 컨텍스트에 실려서 도구 호출 행동을 이끌어요. **새로 입사한 팀원에게 도구를 설명한다고 생각하세요.** 내가 당연하게 아는 맥락, 즉 특수한 질의 형식, 전문 용어의 정의, 자료들 사이의 관계를 **명시적으로** 적어요. 모호함을 피하고, 입력과 출력을 분명히 설명하고 엄격한 데이터 규격으로 강제하세요.

## 5. 일반 사용자에게 적용하기

(이 부분은 개발자용 글을 일반 사용자에게 맞게 제가 풀어 쓴 거예요. 글이 직접 말한 내용은 아니에요.)

내가 코드를 짜지 않아도, AI에게 **파일이나 자료를 주는 일**에 같은 생각을 쓸 수 있어요.

- **자료를 적게, 분명하게:** 폴더에 파일이 수백 개면 AI도 헤매요. 지금 일에 필요한 파일만 주세요.
- **파일 이름과 열 이름에 이름표 달기:** "최종_진짜최종.xlsx"보다 "2026_매출_월별.xlsx"가 좋아요. 열 이름도 뜻이 분명하게 쓰세요.
- **설명서 파일 한 장:** 자료에 "이 폴더는 이런 파일들이고, 이 열은 이런 뜻이야"라는 설명을 붙여 주세요.
- **결과는 짧고 핵심만:** AI에게 "요약해서 줘"라고 하면 다음 단계의 컨텍스트가 덜 차요.

!!! note "★ 한 걸음 더 (심화)"
    - 글은 도구의 성능을 **평가를 만들어 측정**하라고 해요. 도구를 만들고, 평가를 돌리고, Claude Code 같은 에이전트와 협력해서 도구를 자동으로 개선하는 과정이에요. 평가는 다음 페이지에서 다뤄요.
    - 같은 글은 도구가 돌려주는 정보가 너무 많으면 컨텍스트를 낭비하고 너무 적으면 에이전트가 길을 잃는다는 균형을 말하는데, 이 페이지에서는 이 구체적 기법은 확인하지 못했어요.
    - 이전 글(*Building effective AI agents*)은 에이전트와 도구 사이의 접점을 **ACI(agent-computer interface)**라고 부르고, 사람을 위한 인터페이스(HCI)처럼 정성을 들이라고 해요.

## 직접 해보기

AI에게 자주 주는 자료(파일이나 폴더) 하나를 "도구함 점검"해 보세요.

| 점검 | 예 / 아니오 |
|---|---|
| 지금 일에 필요한 파일만 있나요? | |
| 파일 이름만 보고 내용을 알 수 있나요? | |
| 표의 열 이름이 뜻이 분명한가요? | |
| 설명서(한 장)가 있나요? | |
| 개인정보가 들어 있나요? (3장) | |

"아니오"가 있는 칸을 고쳐서 같은 질문을 다시 해 보세요. 답이 달라지나요?

## 오늘 바로 써먹기

1. **AI에게 주는 자료를 줄이세요.** 필요한 것만이 최고의 정리예요.
2. **이름은 미래의 나와 AI가 모두 이해하게 지으세요.**
3. **"이 열은 이런 뜻" 한 줄을 붙이세요.** 설명이 없으면 AI가 추측해요.
4. **결과는 짧게 받으세요.** 긴 도구 결과는 컨텍스트를 채워요.
5. **새 직원에게 설명하듯 쓰세요.** 내가 아는 맥락을 글로 꺼내 놓는 것이 핵심이에요.

## 자주 하는 오해

- "도구가 많을수록 에이전트가 똑똑해진다" → 많으면 고르기 어려워져요. 필요한 것만 두세요.
- "AI가 알아서 파일의 뜻을 안다" → 이름과 설명이 없으면 추측해요.
- "도구는 개발자만 신경 쓰면 된다" → 내가 주는 자료와 설정도 AI에게는 도구예요.
